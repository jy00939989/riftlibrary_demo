# 借阅深化 × 咖啡角 · v2 联合评审（系统 & 机制）

> 评审日期：2026-09-10。两份 v2 分别已吸纳一轮评审意见，**本轮聚焦「两系统叠加后的交互」与「机制完整性」**，不再重复单点数值。
> 前置：我已复核咖啡角对 P2-7 的驳回——**成立，我错了**，`getFacilityLevelCap/getFacilityRequiredStage` 确已建于 `data/atmosphere.js:170/176`，且带「1 阶可升 Lv2」新手保护。本文不再争议此点。

## 结论先行

**两份 v2 各自都很扎实——我的 7+8 条意见基本全部落地（售价对齐 92-98%、升级费 400×1.6ⁿ、Lv2 星蕨前置、废弃"延长停留"、库存加权、×0.25、浮动上限、隐性对价、-1/+5 净+4、温室同批）。**

**但把它们放在一起跑，冒出两个单看发现不了的 P0：**

1. **咖啡角的等级增益会杀死自己的营业**——「借书概率 +5%×Lv」让访客更快借到书离开，进店窗口随之收缩，算下来 **Lv5 的期望收益低于 Lv1**（15.3 → 14.9 币/访客）。升级是负收益。
2. **咖啡角是净 faucet，不是 sink**——借阅 v2 指望着它"对冲"金币通胀，但它建造回本（9-18 天）之后是**永久净流入**（年 +3~6 万）。两个 plan 在金币上是**同向叠加，不是对冲**。

外加：磨损加速会缩小可借书池（与目标相抵）、灵感/好感三路叠加仍无 sink、**两份 plan 都没有定义失败信号**。

## 一、P0-1　咖啡角增益的自我反噬（两 plan 叠加才出现）

### 机制链条

`tickVisitorBrowsing`（`visitors.js:789-792`）的控制流：

```js
const borrowChance = 0.4 + getCurationBorrowBonus();
if (Math.random() > borrowChance) return;   // ← 没借到就 return，跳过后续
attemptBorrow(...);                          // 借到 → status='borrowed'，离开 browsing
```

咖啡角 v2 §2.4.4 的增益是「本次借书概率 **+5%×等级**」（Lv5 = +25%）。而 §2.4.1 规定「**先借阅判定后咖啡角**」。

**若严格按此顺序实现，咖啡角只在「没借到书」的 tick 才有机会**——于是：

> 借书概率越高 → 访客越快离开 browsing → 咖啡角进店窗口越短 → **等级越高，自己越没生意**

### 实测推算（25%/tick 进店）

| 等级 | borrowChance | 期望 browsing 停留 | 每 tick 进店率 | **期望进店/访客** | 单价 | **币/访客** |
|---|---|---|---|---|---|---|
| Lv1 | 0.45 | 2.22 tick | 0.55×0.25=13.8% | **0.305** | 50 | **15.3** |
| Lv2 | 0.50 | 2.00 | 0.50×0.25=12.5% | **0.250** | 110 | **27.5** |
| Lv5 | 0.65 | 1.54 | 0.35×0.25=8.8% | **0.135** | 110 | **14.9** |

**Lv5 的进店率只有 Lv1 的 44%，期望收益反而低于 Lv1。** 玩家花 5,800 金币升满，单位访客收益倒退——这是负向投资。

（Lv2 之所以是最优点，是因为它同时拿到星蕨特调 110 单价、而增益才 +10%。）

### 另外：字面实现有死代码风险

若真把咖啡角判定放在 `if (...) return;` **之后**，该分支**永远不会执行**。这是实现歧义，必须写明插在哪一行。

### 建议（任选）

1. **咖啡角判定提到 borrowChance 判定之前**（每个 browsing tick 都判），与增益解耦——推荐，改动最小
2. 增益改为**不影响 browsing 停留**的收益（好感倍率、还书币加成）
3. 进店判定改挂**访客生成时**（`spawnVisitor`），彻底脱离停留时长

## 二、P0-2　咖啡角是净 faucet，借阅 v2 的"对冲"假设失效

借阅 v2 §六 写：「金币 faucet 增量 +25~45%…**靠咖啡角/展览厅消费口对冲**」。

但咖啡角 v2 的现金流是：

| 项 | 值 | 性质 |
|---|---|---|
| 建造 1500 + 升满 5,800 | **7,300** | **一次性** sink |
| 日均 85-170 币 | 31,000-62,000/年 | **持续** faucet |
| 回本周期 | 9-18 天 | 之后永久净流入 |

→ **净 faucet ≈ +2.4~5.5 万/年**。对照 v4 仿真硬核已过剩（结余 39,402 vs 消耗 21,271），咖啡角会让过剩**再增 60-140%**。

**所以两 plan 在金币上不是对冲，是同向叠加。** 借阅 +25~45% 叠加咖啡角净流入，总 faucet 压力比任一 plan 单独预估的都大。

**建议**：
- 咖啡角补**持续** sink（每日维持费 / 原料采购），否则它只是"延迟 9-18 天的印钞机"
- 或借阅 v2 §六 删掉"靠咖啡角对冲"的表述，改为"金币压力由后续房间计划与首月数据共同校准"
- 两 plan 上线后，**金币日获取量 + 结余增速**应列为联合必看指标（不应各看各的）

## 三、P1-3　磨损加速会缩小可借书池，与"让更多书流通"相抵

- 两 plan 合计磨损加速 **2.5-3 倍**（多本 ×2 + 寄读 ×1）→ 损毁率上升（满磨损 ×1.6）
- 但 `getCompletedBooks()`（`visitors.js:801`）**排除 `damaged` 与 `inRestoration` 的书**
- 损毁后需专注修复（`repairWords = copiedWords × 0.15`），期间该书退出候选池

即：**"让更多书流通"这个目标，其副作用会把书从流通池里拿走。**

粗算：日均借还 7.2 本次（2.4 访客 × 3 本）× 损毁率 ~1%（Lv7 满磨损）≈ **2.2 本/月**进入修复；加速 3 倍后 ~6-7 本/月。对 68 本藏书占比有限，但**修复要吃专注时间**——而专注时间正是生成访客的唯一驱动。

**这才是真正的负反馈闭环**：磨损↑ → 修复专注↑ → 抄新书/吸引访客的专注↓ → 需求与供给同时降。

**建议**：明确「修复时间成本」是否计入净收益评估；上线后观测 `repairWords` 累计量占专注时长的比例，若 >15% 需回调磨损速率或降低修复成本。

## 五、P2-5　两份 plan 都没有失败信号（我的纪律红线）

两份都只有**验收标准**（功能是否正确），没有**"坏掉长什么样"**。按我的流程纪律，没有失败定义的 playtest 等于没做。补上：

**借阅 v2**
| 信号 | 判据 | 含义 |
|---|---|---|
| A | 上线后仍反馈"书借不出去"，且在途书量 <3 本而藏书 >20 | 多本借阅没接住，需回到"去 break"方案 |
| B | 寄读金币占比 > **40%** 总金币收入 | 主链贬值，寄读取代馆内借阅 |
| C | 吐槽:赞叹 触发比 > **3:1** | 负反馈过量，玩家被烦 |

**咖啡角 v2**
| 信号 | 判据 | 含义 |
|---|---|---|
| A | 制作按钮点击率 < **30%**（玩家仍直接兑换种子） | 92-98% 效率对齐仍不够，需再提售价 |
| B | 库存为空的天数占比 > **70%** | 房间长期停摆，供给仍不足 |
| C | **Lv5 单位访客收益 < Lv1** | P0-1 反噬未被修复，升级即亏损 |

> C 这条建议直接写进 verify 脚本第 8 节——它是可自动化断言的。
