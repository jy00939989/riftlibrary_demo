# 古籍保养机制计划 · 评审

> 评审人视角：系统 / 机制 / 数值 / 代码集成。已逐条核对引用文件：
> `js/core/book-progress.js`、`js/capacity.js`、`js/core/focus-session.js`、
> `data/borrow-levels.js`、`js/core/disasters.js`。
> 修复成本基准（`copiedWords×15%`）已实证（disasters.js:122），计划对比口径成立。
>
> 定位：这份计划本身质量高——决策已锁定、数值表自洽、与现有修复/磨损账本对齐。
> 本文只挑**机制层面没说清或没兜住**的点，按严重度排。

## 先结论

计划把"被动修书"补成"主动保养"的体验是对的，数值阶梯（1.5→8%）也诚实表达了"越拖越贵"。
但有一个**没兜住的进度通胀口**（每条保养反复给 +1 氛围），以及一处**机制前提没写清**（保养 vs 修复到底制造什么玩家决策）。
其余是代码集成细节和小钉子。下面按 P0 → P1 → P2 排。

---

## P0 · 氛围可刷（进度通胀口）

**问题**：决策 4 写明"每本 +1 氛围"，且决策 1 写明"无保护期、磨损立即恢复累积"。
两件事叠在一起 = **同一本书可以无限次保养、每次 +1 氛围**。

- 保养成本极低（良好档 `copiedWords×1.5%`，一本 600 字书仅 9 字工时），而一次专注轻松产数百字。
- 书被借出 → 磨损 +1 → 回到良好档 → 再保养 → 又 +1 氛围。跨你全部在架书，每个借还周期扫一遍就是 +N 氛围。
- 氛围是**进度经验值**（驱动阶段阈值 400/900/2800/5600 与设施升级门槛），不是"花掉的钱"，没有 sink。
  计划决策 4 说"不给币与灵感（防刷币口）"——只防了可花货币，漏了**最该防的进度货币**。

这条违反一条铁律：**任何 source 没有对应 sink 或硬闸 = 通胀只是时间问题**。
修复（`applyRepairProgress` book-progress.js:155）也 +1 氛围，但它是**一次性**的（书真坏了才触发，修完 `damaged=false`）。
保养把"一次性"改成了"按需可刷"，性质变了。

**建议（三选一，直接可并）**：
- **A（最干净）**：保养**完全不给氛围**，只留历史 + 墨墨日记（叙事反馈）。保养是"打理动作"不是"奖励动作"，不做成进度来源。
- **B（保留手感）**：+1 氛围改成**每本书每自然日最多一次**（或每借还周期一次），变成"每日打理"小奖励而非无限农场。
- **C（按档差异化）**：氛围只给清掉"濒危→崭新"这种重活，良好档清零不给氛围——从根上打掉 trivial 刷分。

我倾向 **A 或 B**：保养的核心价值应是"避免损坏 downtime + 书况好看"，不是进度快充。

## P1 · 机制前提没写清：保养 vs 修复制造什么决策

计划通篇说"修复系统存活""解决只能看着书越来越破"，但**没说清保养和修复是什么关系、玩家何时选哪个**。
按现有数值，保养**严格占优修复**作为"去磨损"手段：随时可用（wear>0 即可）、永远更便宜（≤8% < 15%）。
那玩家为什么还会让书损坏去走修复？

答案其实在别处，但计划没写：**损坏的书不能外借 → 断借书收入（币/氛围）+ 要花更久修复**。
所以决策张力是"现在花 9 字打理，还是放任直到断收入再花 15% 修"——这是真决策，不是冗余。

**要求**：计划补一段"设计支柱 / 意图决策"，明确写出——
> 保养 = 主动路径（便宜、反复），价值在**避免损坏 downtime**；修复 = 疏忽的安全网（贵 + 断收入惩罚）。
> 二者不是重复 sink，是"勤 vs 懒"的权衡。

没这句话，决策 4 的 +1 氛围就是在真空里拍的（于是漏了通胀口）。这也是我的一条工作纪律：
**每个机制必须能回答"玩家此刻在做什么决策、为什么做"**——计划目前答不上来。

## P1 · 会话类型轴没立起来（代码集成隐患）

计划说"会话类型分支：maintenance 走批次进度（repairOnly 先例 L148）"。
但 `focus-session.js` 当前**没有会话类型字段**——`repairOnly` 是从书状态（`bs.damaged && copyCount≥1`）推导出来的隐式分支（L148）。
而 `pomodoro/countdown/stopwatch` 是**计时模式**，不是**活动类型**。

把 maintenance 当第 4 个隐式分支焊进现有 `repairOnly` 逻辑，会让 `completeFocus` 的分叉越来越脏。
**建议**：显式引入"活动类型"轴（`state.currentSession.activity = 'copy' | 'repair' | 'maintenance'`），
与计时模式正交。维护分支要**显式跳过 `applyWords`**（否则保养会话会推进誊抄进度，如 repairOnly 那样），并独立路由到 `applyMaintenanceProgress`。

## P2 · 修复室速度加成当前是"损坏才生效"，保养要吃需改路径

决策 6 说"保养吃修复室速度加成（+10%/级）"。但 `focus-session.js:115` 的加成**仅在 `bookIsDamaged` 时**进入 `wordsGained`：
```js
const repairSpeedBonus = (bookIsDamaged && isRestorationUnlocked()) ? getRestorationRepairSpeedBonus() : 0;
```
保养的书**不损坏**，所以现有链路里加成是 0。计划必须写明：保养模式要**绕过 `bookIsDamaged` 门槛**单独挂加成，
否则"吃加成"成了一句落不了地的承诺。

## P2 · `copiedWords` 成本基准确实安全，但太脆

已核实：磨损只发生在"被借出"的书，而借出前提是 `completed` → `copiedWords>0`（disasters/visitors 链路）。
所以"磨损书 `copiedWords=0` → 保养白嫖"的洞当前**被不变量堵死**，不是真洞。

但这是**隐式不变量**，计划没写、也没加防御。一旦未来出现"未抄完就被弄脏/获赠即带磨损"的书
（visitor-gift-books、预损书等），`getMaintenanceWords = ceil(0 × rate) = 0` 立刻变免费保养洞。
**建议**：`getMaintenanceWords` 里加 `Math.max(copiedWords, 1)` 或一条断言，把不变量钉死，成本几行。

## 测试补点（并入 §六）

- **氛围闸门**：断言保养完成**不**无条件 +1 氛围（按你选的 A/B/C 改断言）。这是当前 §六 完全没覆盖的一条。
- **速度加成绕过损坏门槛**：保养模式下 `getRestorationRepairSpeedBonus` 生效，不依赖 `damaged`。
- **copiedWords 防御**：传 `copiedWords=0` 时 `getMaintenanceWords ≥ 1`（防未来不变量松动）。
- **重抄完成脏数据**：挂起中同书 copyCount+1 后，批次结算目标以实时 copiedWords 重算或安全剔除。
